apply(state, event): looks at event.type and returns the next state
   TaskCreated      -> adds a task with status "open" and no comments
   TaskCompleted    -> status becomes "completed"
   TaskReopened     -> status becomes "open" again
   TaskCommentAdded -> comment is appended to the comments of the task

getCurrentState(events)
   1. Start with the empty state {}
   2. Call apply for every event, in the order they were stored (reduce)
   3. The last result is the current state -> one TaskState with all tasks = replay (slide 36)

Immutability    -> apply never assigns into the given state
                   - the state is copied with { ...state, [id]: newTask }
                   - the task is copied with { ...task, status: ... }
                   - comments are copied with [...task.comments, comment], no push
                   - the tests freeze the old state (Object.freeze): any write would throw

Events that do not fit
   - event for a task id that does not exist -> ignored, state stays the same
   - second TaskCreated for an existing id   -> ignored, the first one counts
   - unknown event type                      -> ignored
   Reason: events are immutable and stay in the log forever (slide 33), so a replay must never
   fail because of one old event. Checking whether an action is allowed belongs to the place
   where the event is appended, not to the projector.

What the tests also show
   - same events -> same state, every time (replay is deterministic)
   - replaying only the first events gives the state at an earlier point in time (slide 38)
